# dsv4-tiera2-build — source-reproduced production image harness

This directory builds the Deneb production DeepSeek-V4 (b12x) vLLM image
(`dsv4-tiera2:local`) from the reviewable `dsv4-tiera2` patch stack, instead of
from opaque in-image string substitutions. The build output
(`dsv4-tiera2-src:local`) is **byte-identical** to the production image across
the entire `vllm/` source tree (verified: 0 source-file diffs over 3282 files;
only regenerated `.pyc` bytecode differs).

## TL;DR

```bash
./build.sh            # FROM Aiden b12x base + apply patches/dsv4-tiera2.patch
```

## Why this is an overlay, not a from-scratch source build

The b12x MoE/MLA CUDA kernels (CUTLASS / DeepGEMM / FlashInfer artifacts for
`sm120`/`sm121`) are **prebuilt binaries** that exist only inside the Aiden base
image — they cannot be compiled from this (or any) public source tree. The
production image has always been a Python-source overlay on that binary base, so
this harness does the same.

## The core problem: git flat layout vs image nested layout

The decisive design constraint, and why a naive `vllm/` whole-tree COPY from the
`dsv4-tiera2` branch does **not** work:

| | `dsv4-tiera2` git branch | production image (`dsv4-tiera2:local`) |
|---|---|---|
| vLLM base snapshot | `DSV4` @ `eb99b8b` (2026-05-24) | Aiden b12x @ vLLM `1967a5627` (2026-05-27) |
| DeepSeek-V4 model layout | **flat** `vllm/model_executor/models/deepseek_v4_mtp.py` | **nested** `vllm/models/deepseek_v4/{nvidia,amd}/mtp.py` |
| AMD variant | absent | present (`amd/mtp.py`) |

`eb99b8b` and `1967a5627` are **git-diverged** (318 ahead / 127 behind): the two
snapshots straddle an upstream package refactor that moved the DeepSeek-V4 model
from the flat module into a nested per-platform package. Concretely, of the 18
files the patch stack touches:

- **10 files** are byte-identical between the git branch and the image (the
  patches landed the same on both snapshots).
- **6 files** differ between the two snapshots for reasons unrelated to any
  patch (e.g. `gpu_model_runner.py` carries a ~110-line mamba-buffer refactor in
  the image snapshot; `speculator.py`'s `init_attn_backend` is a 3-tuple in
  `eb99b8b` vs a 4-tuple in the image).
- **2 files** are the model package itself (flat single-file in git, nested
  nvidia+amd split in the image).

So the git branch's flat files cannot be dropped 1:1 onto the image without
either landing at the wrong import path or regressing six files to an older
generation. `1967a5627` is verifiably an upstream `vllm-project/vllm` commit
(also mirrored in `aidendle94/vllm`); it is the **exact snapshot the image was
built from** (per `/opt/dsv4/provenance.json` in the image).

## The decision: path-map overlay via a nested unified patch

Rather than rebase the branch onto `1967a5627` (a cross-refactor *port*, not a
clean replay — every model-package hunk would have to be re-expressed for the
nested split, and the 6 snapshot-drift files re-derived), this harness:

1. Starts `FROM aidendle94/sparkrun-vllm-ds4-gb10:production-ready` — the pristine
   `1967a5627` snapshot, which already has the **correct nested layout, correct
   snapshot generation, and the AMD variant**, plus the b12x binaries.
2. Applies `patches/dsv4-tiera2.patch` — the complete `base -> dsv4-tiera2`
   delta (18 files, 54 hunks) expressed against the image's **nested** paths.
   This single patch encodes the same transformation chain the image was built
   with:
   - **base-tier (5 PRs):** #43733 #43445 #42971 #44253 #44420
   - **leakfix (deneb#2289):** `block_pool.py` + `single_type_kv_cache_manager.py`
   - **new-tier (4 PRs):** #43961 #44821 #43991 #44603
   - (#43988 intentionally skipped — see the branch `DSV4_TIERA2.md`.)

The patch is the **nested-layout source-of-record**; the branch `DSV4_TIERA2.md`
is the per-PR human-readable provenance. They describe the same 18-file delta —
one as a nested patch, one as prose against the flat layout.

### Regenerating the patch

`patches/dsv4-tiera2.patch` was generated by diffing the pristine base against
the production image, per touched file, with git-style `a/ b/` prefixes (apply
at `site-packages` root with `-p1`):

```bash
BASE=aidendle94/sparkrun-vllm-ds4-gb10:production-ready
TGT=dsv4-tiera2:local
# for each touched file f: diff -u base/f tgt/f --label a/f --label b/f
```

If a future change adds/removes a PR, regenerate against the new target image
(or extend the patch hunks directly) and re-verify 0 source-diff.

## Verification (performed)

- `git apply --check` passes against the pristine base (patch applies cleanly).
- AST gate: all 18 patched files parse.
- Import smoke: `import vllm` (== `0.21.1rc1.dev339+g1967a5627bc3`) and direct
  import of every patched module (nested `deepseek_v4.{nvidia,amd}.mtp`, eagle
  speculator, KV cache manager, cudagraph_utils) succeed.
- **Byte-equality:** full `vllm/` source-tree sha256 comparison vs
  `dsv4-tiera2:local` → **0 differing source files** (3282 files); only
  regenerated `.pyc` bytecode differs.
- Weight-loading serve smoke intentionally skipped: the source tree is byte-
  identical to the already-validated production image and the b12x binaries are
  inherited unchanged, so a serve would only re-test validated code while
  contending for GB10 unified memory with the live fleet.

## Next steps — porting to vLLM 0.23

This harness pins the `0.21.1rc1.dev339` (`1967a5627`) snapshot via the Aiden
binary base. Moving to 0.23 means a new binary base, so the path forward is:

1. Obtain (or build) a b12x binary base on the target 0.23 vLLM snapshot. The
   kernels still must come prebuilt — confirm the 0.23 base ships the
   `sm120/sm121` CUTLASS/DeepGEMM/FlashInfer artifacts.
2. Re-anchor the 18-file delta against the 0.23 tree. Most hunks are the merged
   upstream PRs (#43733/#43445/#42971/#44253/#44420/#43961/#44821/#43991/#44603),
   so on a 0.23 base they should already be present — the patch likely **shrinks
   to just the leakfix (deneb#2289) + any still-unmerged carry**. Re-run
   `git apply --check`; drop hunks that no longer apply because upstream already
   has them.
3. Keep the same verification loop: AST gate, import smoke, and a 0-source-diff
   check against whatever the 0.23 production image becomes.

## `reference-apply-scripts/`

The original anchored-substitution scripts that built the **new-tier** layer of
the production image (`dsv4-tiera:local -> dsv4-tiera2:local`), preserved here as
per-hunk rationale. Each carries a docstring explaining *why* the hunk is dsv4-
relevant and how its anchor was verified `count==1` against the running image.
The `patches/dsv4-tiera2.patch` hunks for #43961/#44821/#43991/#44603 are the
byte-equivalent of running these scripts on the nested base; the scripts are kept
for review/audit and as a template when re-anchoring for the 0.23 port.
